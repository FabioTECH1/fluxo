# Native acceptance for interrupted historical installer recovery

Use an explicitly approved, disposable Ubuntu Noble Cronie fixture. The parent operator verifies the exact selected VM hostname, root, and `FLUXO_PHP_UPDATE_VM_TEST=1` inside the guest before fault injection, service changes or an approved reboot. Retain evidence outside the guest. Run the task-only case and the combined Scheduler/task case from their respective historical baselines.

1. Start with a genuine schema1/2 task registration acknowledged by Cronie generation A. For the combined case also retain unresolved historical Scheduler retirement evidence. Record kernel boot ID, provider/configuration, registration, trigger, helper and invocation history. After natural job drainage, replace the Cronie generation on the same boot under the same configuration. Confirm B has a different daemon generation and cgroup inode. Use the normal installer for the exact candidate artifact and retain its digest and version.
2. Inject process loss at the first attempted publication of `/var/lib/fluxo/execution-readers.json`. For example, run the installer under a root syscall debugger following fork/exec and all threads. Trap rename/renameat/renameat2 **on entry** in the installed Fluxo process, filter by that exact destination pathname, and kill that process while the rename is stopped. This places the interruption after the fsynced task-core write. Allow the installer to report failure. Check that the floor is absent, the installer pointer is pending, and the live task core matches the plan's target bytes including B, the planned nonce and `received: false`. Check that the trigger still has the archived predecessor bytes. Record the operation UUID and SHA-256 of the plan, archived image and each before-file. Discard a run that missed this boundary.
3. After natural drainage, replace B with Cronie C on the same boot. Rerun the exact same installer. Require the operator-approved reboot diagnostic, the same pending pointer/archives, the same unacknowledged core, and the original trigger. Capture the actual guest boot ID before reboot. At this point the parent operator approves and performs a real guest reboot.
4. Confirm `/proc/sys/kernel/random/boot_id` differs from both archived identities. Record the new Cronie identity under the same policy. Rerun the same release's normal installer. Observe the committed floor by following the rename syscall as above, this time stopping on successful return of the committed-floor rename while the process still holds the activation gates. Capture the floor and task core, then continue the installer. Verify the original operation UUID, immutable plan and archive hashes, original planned B target, planned nonce, retained helper and `received: false`. For combined conversion also require the original pending Scheduler retirement marker and retained source evidence.
5. Allow genuine cron ticks and capture the resulting registration, boot ID, provider identity, helper, nonce and installer outcome. Require the new-boot acknowledgement to bind the observed live Cronie identity, with the archived B target and source history still intact. For the combined case track Scheduler retirement, loader publication and their genuine acknowledgements independently through readiness. Check panel restoration against the original installer intent. Record image and script digests, guest architecture and actual boot IDs with the results.
